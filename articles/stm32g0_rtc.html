STM32 RTC Explained

On STM32 microcontrollers, the Real-Time Clock (RTC) is hardware that is provided for the purposes of tracking time. More specifically, for tracking human-comprehensible time like seconds, minutes, hours.

If you want to track highly specific microsecond or even nanosecond intervals, STM32's timers are what you need - they count clock cycles so you can track some seriously small intervals.

Overview

Unlike timers (which are made to be highly precise), the RTC is made to be available in low-power modes with a tradeoff: it is less precise and so is used for things that tolerate this lower precision.

This means that the RTC is available in the various power modes: RUN, STOP, SUSPEND, STANDBY.

Additionally, since the backup domain can remain powered by VBAT (backup battery power supply) even when VDD (main power supply) is gone, the RTC can even continue working during power outages (both deliberate and unexpected).

Clock Sources

Inside of the RCC_BDCR register, you will find a 2-bit field called RTCSEL - that is how the RTC's clock source* is selected.

From RM0444[1], the 4 options are:

  • 00: no clock selected
  • 01: LSE
  • 10: LSI
  • 11: HSE/32

The selection is important for a few reasons.

Firstly, if you are writing code for a low-power application, you probably want to use a clock source that's already on instead of enabling and dedicating an entire clock source for the RTC.

Secondly, the LSI is less precise than the other two, so you'd only use it for short-term time tracking as it'll become inaccurate significantly quicker.

And thirdly, the three clocks are available in different power modes, with LSE being the only one available when VDD is absent.

It's also worth factoring in that once written, these bits are unable to be changed until the RTC domain is reset, or a failure is detected on the LSE (LSECSSD bit is set). If you do want to remove the selected clock and go back to option '00: no clock selected', you can do that at any time by writing BDRST bit. Both of these mentioned bits are located in the same register.

Once the clock source is selected, it's ran through two prescalers before it becomes the final kernel clock (ck_spre). The crucial thing here is that the final kernel clock must be 1 Hz if you want the speed of the clock to be the same as your standard wall clock that tracks seconds, minutes, hours. Any faster or slower than 1 Hz and the RTC will track time faster/slower at the same rate (e.g. a 2 Hz clock will make 1 real-life second be counted as 2 seconds in RTC time).

Here's the formula for the kernel clock:

ck_spre = RTCCLK / ((PREDIV_A + 1) * (PREDIV_S + 1))

* Note this is the kernel clock, NOT the peripheral clock. The RCC article has more info on the difference between these two, but in short, the peripheral clock controls access to registers, whereas the kernel clock controls the actual functionality of the peripheral. In the case of RTC, the main functionality is keeping track of time.

RTC Registers

Once you have the RTC running, the way you see the time is through registers:

  • RTC_TR: time register, shows the time (hours/minutes/seconds in BCD format, and an AM/PM bit)
  • RTC_DR: date register, shows date (year/month/weekday/day in BCD format)
  • RTC_SSR: sub-second register, see description and formula below
  • RTC_CR: control register, lets you control various aspects of the RTC that this article covers

Sub-Second Register

As the name implies, this involves subseconds.

It works by counting down from PREDIV_S (one of the two prescalers) to 0, so a fractional second is obtained with this formula:

Second fraction = (PREDIV_S - SS) / (PREDIV_S + 1)

Shadow Registers

You might be wondering what happens if you read the time from the TR register at 23:59:59, the RTC ticks over to the next date, and then you read the date from the DR register.

Logically, you think you would read 23:59:59 on the current date, then read tomorrow's date as we tick over into the next day, making the code believe it's a whole day ahead.

However, this doesn't happen as long as you access the registers in the right order.

You see, the TR, DR, and SSR are updated through shadow registers which are synchronised to the RTC every 2 RTCCLK clock cycles.

Since the 3 aforementioned registers aren't directly synced to the RTC, it allowed the hardware designers to do one thing: when the TR register is read, DR and SSR become locked and are not updated until DR is read.

This means they will always be synced as long as TR is read first, and DR last (you may or may not read SSR, that is up to you as the developer).

It is possible to bypass the shadow registers and read from the calendar directly, meaning you lose the ability to lock DR/SSR after a TR read and risk a rollover, but there is probably a scenario where it is useful. The bypass can be achieved by setting the BYPSHAD bit in RTC_CR.

Write Protections

By default, the RTC registers are protected from write accesses in 2 ways.

Firstly, the entire backup domain (that means the RTC and backup registers) is write-protected after a reset and can only be enabled by setting the DBP to 1 in the PWR_CR1 control register.

The second way is with the RTC_WPR register: writing the correct sequence to it enables writes to the other RTC registers. The sequence is:

  1. Write 0xCA to the RTC_WPR register
  2. Write 0x53 to the RTC_WPR register

Note that BOTH of these need to be met to enable writes to the RTC, and since the RTC is write-protected (including the RTC_WPR register) until DBP is set, that means DBP must be set first, then the correct sequence is to be written in RTC_WPR.

Init Mode

To give the RTC an initial time reference (so it starts from a date/time we want it to), it IS as easy as just writing it into the RTC_TR/RTC_DR registers, however it must happen in something called "init mode".

When init mode is entered, the RTC calendar is stopped and thus the TR/DR registers are not updated, allowing writes into them.

To enter init mode:

  1. Set the INIT bit in the RTC_CR control register
  2. Poll the INITF bit in the RTC_ICSR register
  3. When INITF is automatically set by hardware, init mode has been entered
  4. Clear the INITF bit when done to exit init mode

It takes about 2 RTCCLK clock cycles for INITF to be set due to synchronisation.
