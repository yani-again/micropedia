NMEA 0183 Protocol For uBLOX Modules

In 1983, the National Marine Electronics Association created a data transmission protocol that made it easy for different manufacturers of electrical equipment to ensure compatibility during data transfers, and it was created for the US maritime sector.

Today, people like me use it for their personal projects!

This will be a short article and focused on usage of the NMEA 0183 standard specifically in uBLOX GNSS modules, so strap in!

There is a newer protocol - NMEA 2000 - made in 2001, which is an improvement on 0183 and serves it purpose more robustly, but 0183 is still widely used today and works perfectly fine for things like basic GNSS/GPS modules (and way more), so it's worth learning for that sake.

NMEA Messages

Here's an example of different messages (called 'sentences') you'd see from a GNSS/GPS module that uses the NMEA protocol:

$GPGGA, 161229.487, 3723.2475, N, 12158.3416, W, 1, 07, 1.0, 9.0, M, , , , 0000*18
$GPGLL, 3723.2475, N, 12158.3416, W, 161229.487, A, A*41
$GPVTG, 309.62, T, , M, 0.13, N, 0.2, K, A*23

You'll really quickly start to notice the pattern - they all begin with a dollar $ sign, have some gibberish-looking letters that start with 'GP', and then there are a bunch of values separated by commas.

Unlike a lot of things in the embedded systems world, this really is that simple!

NMEA Overview

NMEA messages are structured as follows:

$IDSentence TypeData*/th>ChecksumTerminator
  • $: the literal dollar symbol is used as a delimiter to signal the start of every new message
  • ID: talker ID made of 2 characters, signals which satellite constellation produced the sentence (see options below)
  • Sentence Type: 3-character ID to signal what kind of data is incoming (see its dedicated section)
  • Data: comma-separated fields of data
  • *: checksum delimiter, signals beginning of checksum field
  • Checksum: 2-character hex checksum
  • Terminator: sequence that ends the message

Message Start Delimiter

This is the dollar symbol I mentioned in the example and the table with the structure above.

It's the literal dollar $ character (ASCII value 0x24).

So whenever you see this after a terminator sequence, it marks the beginning of a new sentence and the next part is the talker ID.

Talker ID

The device which is transmitting the data uses this to identify which constellation produced the sentence.

In case you're unaware, GNSS uses satellites from different countries to get its location fix, and the collection of a country's satellites is called a constellation.

These are the possible 2-character values for GNSS modules:

  • GP: GPS (USA)
  • GL: GLONASS (Russia)
  • GA: Galileo (Europe)
  • GB: BeiDou (China)
  • GQ: QZSS (Japan)
  • GN: multi-constellation

Generally multi-constellation is more reliable.

Sentence Type

This is the 3-character sequence which outlines what the following data field means.

NMEA 0183 defines multiple standard sentence types, here is a list of the ones used by my uBLOX Max-M10S module:

DTM (Datum Reference)

One of the definitions of 'datum' is "A point, line, or surface used as a reference, as in surveying, mapping, or geology."

GPS serves your location as a set of coordinates. Those coordinates need to be relative to something, just like with a graph in maths - if you don't know where (0,0) is, you can't plot the location of (1,1). Besides that, since the Earth is an ellipsoid (not a perfect sphere) and its geometry varies from continent to continent, it's sometimes better to use a local datum (for the specific continent you'll be in) in order to get a more accurate local ellipsoid, improving the accuracy for that specific region.

There are a few common options, though the standard one is WGS84. It was designed to be a good global average, though for better precision you can use a local datum.

Anyway, this message contains information about the datum in use and the reference datum.

When you switch datums, there is a calculation you need to perform so you can get the right coordinates when you factor in the offset from switching datums, but for the project I'm working on I'm unsure if I yet need to do this, so I will not include that unless I come to the conclusion that I do.

Sentence structure:

$xxDTM,datum,subDatum,lat,NS,lon,EW,alt,refDatum*cs\r\n

GxQ

This exact message implementation is proprietary to uBLOX modules. The GxQ messages are part of NMEA 0183, but the EI part is not.

This is a collection of 6 messages which are used to poll a specific constellation and receive location data from it at the next available opportunity:

  • GAQ: Galileo satellites
  • GBQ: BeiDou satellites
  • GLQ: GLONASS satellites
  • GNQ: multi-constellation satellites
  • GPQ: GPS satellites
  • GQQ: QZSS satellites

The talker ID for this sentence is EI as outlined in the uBLOX interface description document, and you also need to include the kind of sentence you want to poll for.

E.g. if you want to request the RMC message specifically from Galileo satellites, you'd send this over serial:

$EIGAQ,RMC*2B\r\n

Then, the GNSS transceiver will send the $GARMC message at its earliest convenience.

GLL

This is where the "real" location data lies. The GLL message contains data on:

  • latitude
  • longitude
  • North/South and East/West indicator
  • UTC time (in hhmmss.ss format)
  • positioning mode flag

And a few other things, but the ones above are what you'd mostly care about.

Those are mostly all clear, except the positioning mode flag, that one is a single ASCII character which indicates the validity of the rest of the data, and different letters can be used to mean the same thing across the different messages which integrate these flags.

The uBLOX interface description document has a table with all of them.

Sentence structure:

$xxGLL,lat,NS,lon,EW,time,status,posMode*cs\r\n

GNS

GNS is almost like a superset of GLL - it still has the same lat/long, compass direction, and UTC time data, however it additionally introduces a few extra fields:

  • amount of satellites used
  • altitude (above sea level)
  • separate positioning mode flags for GPS, GLONASS, Galileo, and BeiDou

Sentence structure:

$xxGNS,time,lat,NS,lon,EW,posMode,numSV,HDOP,alt,sep,diffAge,diffStation,navStatus*cs\r\n

GGA

Think of it as GNS without the multi-constillation positioning mode stuff.

In short, every single one of GLL, GNS, and GGA give you the location coordinates and UTC time alongside at least one flag (GLL), while others also include things like DOP and amount of satellites (GNS/GGA).

Sentence structure:

$xxGGA,time,lat,NS,lon,EW,quality,numSV,HDOP,alt,altUnit,sep,sepUnit,diffAge,diffStation*cs\r\n

RMC

This provides coordinate data just like the last 3 messages, but has a different use.

While those focus on transmitting the data with clear flags on how quality it is, RMC focuses on the navigation by also including speed and course (direction the module is actually moving in), but it lacks altitude measurements.

Additionally, it includes the date - the last 3 messages only included UTC time, without the day, month, and year.

Sentence structure:

$xxRMC,time,status,lat,NS,lon,EW,spd,cog,date,mv,mvEW,posMode,navStatus*cs\r\n

TXT

These are just metadata from the GNSS module.

Information like firmware version is presented here and can be useful for debugging.

The only really useful one I've seen besides that is the ANTSTATUS one, which tells you if the antenna is okay or not - could be useful to go into some kind of distress or recovery mode when the antenna isn't ok.

Sentence structure:

$xxTXT,numMsg,msgNum,msgType,text*cs\r\n
